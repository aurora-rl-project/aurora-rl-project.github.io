跨区域强化学习

SparrowRL 让大模型 RL 能在灵活租用的跨云 GPU 上运行，即使这些 GPU 只通过普通 1–10 Gbps 链路连接。它只发送每步真正变化的约 1% 权重对应的无损稀疏 delta，接近 RDMA 集群吞吐。

强化学习正在塑造今天最强的推理模型。但运行这些训练的系统，默认假设团队拥有一整排通过百 Gbps RDMA 连接的 GPU。大多数团队并没有这种条件。SparrowRL 去掉这个假设，让跨供应商、跨区域灵活租用的 GPU 容量也能接近专用 RDMA 集群的速度。

面向谁为什么跨区域 RL 重要

过去几年，RL 后训练几乎只属于能预留百 Gbps RDMA 超级集群的团队。这一步能把有能力的基础模型变成强推理模型。单个 GPU 往往可以跨供应商、跨区域灵活租用。真正难以按需获得的是把它们连成一个集群的高速互联。没有这种网络，权重同步墙就会把 RL 训练挡在门外。SparrowRL 移除这个障碍，让严肃的 RL 后训练可以跑在灵活、松耦合的 GPU 上。

因此，跨区域 RL 不只是部署技巧。它关乎成本和可及性：我们能否让 RL 后训练足够便宜、足够灵活、足够可靠，让更广泛的研究社区都能参与？如果答案仍然依赖预留 RDMA 集群，大多数团队都会被排除在外。如果普通 GPU 可以被拼接起来，RL 就会成为更多团队可以实际使用的工具。

对学术实验室和小团队, SparrowRL 把采购壁垒变成系统问题。团队不必先建立供应商关系、预留固定的 RDMA GPU 集群，也不必在实验尚未验证前就支付长周期配额。它们可以把真正能拿到的 GPU 组装起来：本地机器、按需云实例、合作机构的空闲算力。先小规模启动，GPU 出现时再加入，实验结束后立即停止。SparrowRL 让这种拼接式资源也能支撑严肃的 RL 后训练：基础设施更便宜，调度更灵活，也不需要私有超级集群。

对大规模部署，解耦式 RL 正变得越来越重要，原因很实际：Trainer 和 rollout 池并不需要同一种硬件。策略优化主要受密集训练计算主导，更适合放在互联紧密的高端 GPU 集群上。Rollout 解码常常受显存带宽和容量限制，因此可以利用更便宜、更异构的加速器。大型供应商和实验室本来就有分散在不同区域、云和硬件代际上的 GPU。机会在于把这组碎片化资源变成一个 RL 系统，但阻塞点是策略刷新：全量权重同步会让远端 rollout 容量很难保持最新，也很难经济地接入训练循环。SparrowRL 降低这条链路的网络开销：Trainer 留在互联条件最好的集群上，rollout 容量则从任何有 GPU 的地方拉起。稀疏 delta、Relay 扇出和版本感知调度，让系统真正利用全球 GPU 池，而不是让远端资源困在慢速跨区域链路之后。

图 1 对比了两种运行模式：一边是预留 RDMA 超级集群，另一边是分散在多个区域的按需 GPU。

RL 后训练遵循一个简单循环：Trainer 更新策略，然后把新权重广播给一组生成样本并回传的 Rollout Actor。问题就在这个广播。RL 每一步都要刷新整个模型，因此权重传输正好落在关键路径上，并随模型规模线性增长。在数据中心 RDMA 网络里，这个开销几乎不可见。在跨区域网络里，它就是核心瓶颈。

瓶颈为什么 RL 需要超级计算机

以 8B 模型为例。BF16 权重约为 16 GB，而且每一步都必须发送到每个 Actor。100 Gbps RDMA 链路上的同步大约需要 1.3 秒，可以轻松隐藏在 Actor 约 45 秒的生成窗口中（图 2）。如果换成 1 Gbps 跨云链路，同步时间会膨胀到 128 秒，远远超过生成本身。即使是一阶段异步流水，也无法隐藏比被重叠任务还长的传输，GPU 利用率会跌到个位数。

这就是为什么 OpenRLHF、veRL、StreamRL 等先进 RL 系统都面向紧耦合 RDMA 集群。而这种集群恰恰是大多数团队难以获得的：

  • 网络溢价。 RDMA 节点比普通以太网节点更贵：某供应商上 16×H100 约为 ~$39/hr，而普通网络约为 ~$31/hr，仅网络就多出 26%。
  • 最小预留周期。 供应商通常要求 24 小时到一周的预留。一个探索性的 48 小时实验，可能变成一周账单，成本最高放大到 3.5×。
  • 采购门槛。 预留大规模 RDMA 资源通常需要销售关系和信用额度，而学术实验室、政府团队和创业公司往往没有这些条件。

与此同时，从两个云上按需拼接同样 16 张 GPU，成本约为 ~$26–27/hr，并且计费更灵活。算力就在那儿，只是藏在 1–10 Gbps 跨区域链路之后。阻挡这些按需算力进入真实 RL 训练的唯一问题，就是权重同步墙。因此我们提出问题：普通跨区域网络能否提供 RDMA 级别的 RL 吞吐？

关键洞察RL 每步几乎不改变模型

面对带宽问题，常见做法是堆更多带宽。我们反过来看：不要把 RL 循环当作黑盒，而是打开它，看清楚到底在传什么。答案很惊人。预训练中，梯度下降几乎每步都会推动所有参数；但单步 RL 更新后，绝大多数权重保持逐 bit 不变。

我们测量 element-wise nonzero ratio，也就是连续 checkpoint 之间发生变化的标量参数比例。结果显示，每步真正改变的元素只有约 1%（图 3）。其余 99% 逐 bit 相同。这种更新是细粒度稀疏的：几乎每个张量都会有一些变化，但每个张量内部只触及极少数离散元素。

为什么 RL 如此稀疏？ 第一，RL 后训练通常使用 1e-6 量级的小学习率，比预训练低约两个数量级，因此每一步只是在轻微调整模型。第二，在线 RL 更新具有 in-distribution 特性，近期理论将其与更少遗忘和更小参数移动联系起来。第三，KL 惩罚、梯度裁剪等正则项会进一步限制每一步的移动幅度。这个现象会持续存在：非零更新比例很快降到 1% 以下，并在 800 步内保持稳定。

BF16 rollout serving 会进一步放大这种稀疏性。Trainer 可能更新 FP32 master weights，但 Actor 接收的是 BF16 checkpoint；低于 BF16 表示间隔的 FP32 小更新会在推理前被舍入掉。因此，SparrowRL 测量并传输 Actor 真正需要的 BF16 inference-side delta。FP16 有更细的尾数精度，但动态范围更窄，在这类 serving 路径中更少使用，因为它增加下溢风险并常常需要 loss scaling。

机会 → 全量权重广播约 99% 的字节都在重传没有变化的权重。改为发送无损差分，就不会改变训练动态。

系统SparrowRL 如何工作

SparrowRL 将这一观察转化为系统。它复用了 PRIME-RL 的部分训练和推理代码，包括 PyTorch FSDP2 训练组件和 vLLM 推理组件。实现约为 4.3K 行 Python，并不改变底层 RL 算法。三个机制协同工作（图 4）。

1 · 无损稀疏 delta

SparrowRL 不发送临时广播，而是让每一步都生成一个带版本、不可变的 artifact，其中只包含发生变化的元素，并保留完整精度。没有量化，也没有丢弃更新；Actor 收到的正是 Trainer 计算出的 bit。把 checkpoint 存储和网络传输统一成一个对象，也让重试变得明确：一个 rollout 要么匹配已验证的版本 hash，要么结果会被拒绝。

朴素做法会把每个变化表示为 (index, value)，其中 4 字节 index 比 2 字节 value 还重。SparrowRL 分两步降低开销。它先存储排序后 index 之间的差值，再用 LEB128 变长整数编码这些差值（图 5）。小 gap 只占 1 字节，少数大 gap 才会扩展到第 2 字节。这样 index 平均从 4 字节降到不到 2 字节，checkpoint 又缩小 30–50%。

2 · 流式传输

稀疏 delta 是可分解的，所以 SparrowRL 不必等待整个文件生成。它把每个 delta 切成 segment，并在其余部分仍在提取时就发送第一个 segment，从 trainer 到 relay 再到 actor 形成 cut-through 路径（图 6）。segment 会以 round-robin 方式分布到多个 TCP stream 上。某个 stream 因丢包停顿时，不会阻塞其他 stream，因此 WAN 链路能保持饱和。在我们的美国–加拿大部署中，多流传输把 202 MB delta 从 4.71 秒降到 2.90 秒。关键是，传输与 rollout 生成重叠。Actor 在当前版本上生成时，提前 stage 下一版本，并在 batch 间安全点原地 commit。rollout 永远不会来自半应用的模型。

3 · 面向复杂 GPU 池的调度

松耦合 Actor 的速度可能相差 2–3×（H100 vs A100 vs L40），而且链路拥塞、GPU 降频、spot 实例消失都会让差距漂移。SparrowRL 根据实测吞吐为每个 Actor 分配任务，并用 tokens/s 的 EMA 更新估计。一个 5,000 tok/s 的 H100 和一个 2,500 tok/s 的 A100 会把 300 个 prompt 按 200/100 分配，并一起完成。一个反馈信号即可吸收 GPU 降频、网络拥塞和资源争用，而不必分别追踪。版本感知 gating 防止陈旧 Actor 污染训练步。限时 lease 处理故障：如果某个 Actor 或区域错过 deadline，它的 prompt 会回到池中，由健康 Actor 接管。只有 lease 有效且版本和 checkpoint hash 都匹配时，结果才会被接收。

证据效果是否成立？

主要端到端评估使用 Qwen3 4B/8B/14B，Trainer 位于美国 H100，A100 rollout Actor 位于加拿大。真实跨云链路在 ~500 Mbps 到 1 Gbps 间波动。额外压力测试模拟 0.25–10 Gbps 链路，将 Actor 分散到加拿大、日本、荷兰和冰岛，在加拿大–澳大利亚部署中评估 Relay 扇出，并混合 A100/L40 Actor 来测试异构性。基线包括 vanilla cross-DC 全量权重广播、其 multi-stream 变体，以及理想化 800 Gbps RDMA 上界 Ideal-SingleDC。每步现在只传 202 MB 稀疏 delta，而不是 15.6 GB 全量权重，缩减 79×。即使在 0.25 Gbps 下，delta 也能在数秒内传完；全量广播需要 566 秒。

从设计上无损

SparrowRL 发送的是无损 delta，而不是压缩梯度或量化近似。在相同的一步异步调度下，Actor 收到的策略更新与全量权重刷新会传递的更新一致。系统改变的是字节如何移动，而不是 RL 目标、rollout 策略语义或优化器更新。

这就是论文将 SparrowRL 定位为“不牺牲准确率而提升吞吐”的原因。稀疏 delta 传输保留非零值的完整精度，并且只在安全的版本切换点激活更新。你可以在普通链路上获得接近高带宽网络的吞吐，而不把模型质量变成压缩权衡。
